# Research notes

Distilled from the 2026-09-13 research sweep: 8 parallel researchers, each load-bearing claim
checked by an adversarial verifier, then synthesized and critiqued. Kept in the repo because the
raw output lives in a session temp directory that will eventually be deleted.

The corrected-claims section is the valuable part. These are things that are widely repeated and
wrong, including in the five reference projects hull was inspired by. Several would have put real
bugs in hull if taken at face value.

## Corrected claims

- lizzie.io seccomp 'sets no_new_privs': REFUTED. contained.c calls seccomp_attr_set(ctx, SCMP_FLTATR_CTL_NNP, 0), which leaves NNP OFF. Her 'ping won't work' remark is the reason she disabled it. The filter only loads because CAP_SYS_ADMIN is held in the user namespace. A new runtime should set NNP=1. https://man7.org/linux/man-pages/man3/seccomp_attr_set.3.html
- lizzie.io rationale for unsharing CLONE_NEWUSER late: MISATTRIBUTED. The 'complete set of capabilities' quote is from a footnote about capability semantics. Her actual reasons were (1) a process cannot usefully write its own uid maps, so the parent writes them, and (2) the user namespace is optional, with a fallback when unsupported. The technical point still holds: container root cannot mount proc, sysfs or devpts. https://blog.lizzie.io/linux-containers-in-500-loc.html
- lizzie.io blkio.weight=10: WRONG. The code writes "64" because it uses the PIDS macro by mistake. WEIGHT="10" is never used, and the prose says 50. memory.kmem.limit_in_bytes is still enforced on WSL's 5.15 kernel; it became a no-op only from 5.16. Another bug not in the original claim: the parent closes fd 0 (stdin) through a double close. https://blog.lizzie.io/linux-containers-in-500-loc/contained.c
- Liz Rice PR #13 'merged 2022': CORRECTED. It was authored 2022-10-02 and merged 2025-08-12. The regression stands: cg() runs after chroot, so the pids limit most likely does nothing. https://github.com/lizrice/containers-from-scratch/pull/13
- libcgroup gained cgroup v2 in 3.x: WRONG. All tools got v2 support in v2.0 (May 2021); systemd scope support came in 3.1.0. systemd first refused to boot on v1 by default in v256, not v257, and v258 removed v1 entirely. https://github.com/libcgroup/libcgroup/releases/tag/v2.0
- bocker's 02:42 MAC prefix 'is Docker's prefix per issue #17': WRONG. Issue #17 only asks why that prefix was chosen. Docker Engine 28 now generates random MACs (moby#48808). The gateway IP collision also affects ps_42010, not only ps_42100. https://docs.docker.com/engine/release-notes/28/
- Docker Hub 'returns an OCI index regardless of Accept': OVERGENERALIZED. Hub returns whatever manifest type was pushed for that tag and ignores Accept. Older tags return a Docker manifest list v2, and some (e.g. busybox:1.24) return schema1 even when only v2 is requested. Clients must dispatch on Content-Type or mediaType. mocker actually fails first at manifest['name'].
- rubber-docker rd.py is 'the final, correct operation order': OVERSTATED. It is the level-10 skeleton; setuid is still a TODO, it joins cgroups from inside the child before extracting the image, and it has no capabilities, seccomp or user namespace. pivot_root corrections: the MS_SHARED restriction applies to the parent mounts (and put_old), not to new_root's own mount; the current root must itself be a mount point; EBUSY means new_root or put_old is on the current root mount. https://man7.org/linux/man-pages/man2/pivot_root.2.html
- crun uses CLONE_INTO_CGROUP for exec 'since 1.7': WRONG. It has done so since crun 1.4. Version 1.7 added clone3 for joining cgroups at create time with the cgroupfs driver. CLONE_INTO_CGROUP can also fail on cgroup v2 rule violations, not only with ENOSYS. https://github.com/containers/crun/blob/main/NEWS
- containerd schema1 can be re-enabled with CONTAINERD_ENABLE_DEPRECATED_PULL_SCHEMA_1_IMAGE: TRUE ONLY FOR 2.0.x. containerd 2.1 removed schema1 entirely (PR #11681). Docker disabled it by default in v26 and removed it in v28.2. https://github.com/containerd/containerd/pull/11681
- Moby uses a mknodChar0Overlay trick for rootless whiteouts: OUTDATED. That code existed only in early 20.10. Kernels 5.8+ allow unprivileged 0/0 whiteout mknod. Podman documents native rootless overlay as needing Podman 3.1+ on kernel 5.12+, not 5.13.
- Current BuildKit built-in ARGs include BUILDKIT_HISTORY_PROVENANCE_V1: OUTDATED. The Dockerfile 1.27.0 list is BUILDKIT_BUILD_NAME, BUILDKIT_CACHE_MOUNT_NS, BUILDKIT_CONTEXT_KEEP_GIT_DIR, BUILDKIT_GIT_ADVICE, BUILDKIT_INLINE_CACHE, BUILDKIT_MULTI_PLATFORM, BUILDKIT_SANDBOX_HOSTNAME, BUILDKIT_SYNTAX and SOURCE_DATE_EPOCH. https://raw.githubusercontent.com/moby/buildkit/master/frontend/dockerfile/docs/reference.md
- The OCI image config has no Healthcheck: PARTLY WRONG. OCI reserves the Healthcheck key (alongside Memory, MemorySwap and CpuShares) without defining it. Only OnBuild and Shell are completely absent. OCI history entries also include 'author'. https://github.com/opencontainers/image-spec/blob/main/config.md
- buildah/podman use BuildKit's Dockerfile parser via imagebuilder: WRONG. openshift/imagebuilder has its own forked parser (its own Node type, dispatch table and Parse) and reuses only BuildKit's heredoc helpers and shell lexer. https://raw.githubusercontent.com/openshift/imagebuilder/master/dockerfile/parser/parser.go
- overlayfs lowerdir+/datadir+ 'since 6.8': SOURCES CONFLICT. One verifier found it documented in v6.7 and included in the 6.7 overlayfs pull (and backported to 6.6 stable and WSL 6.6.y); another quoted the docs as saying 'Since kernel v6.8'. Treat it as 6.7+ and probe at runtime. Layers passed by fd (FSCONFIG_SET_FD) need 6.13+.
- Moby falls back to the naive (slow) diff when metacopy is on: WRONG. It falls back only for redirect_dir (and an opaque copy-up bug); metacopy is detected and reported but does not trigger fallback. https://github.com/moby/moby/pull/34342
- WSL #10926 (mirrored-mode container access to LAN services) is open: WRONG. It is closed as completed. moby#48201 is still open. A current problem to add: WSL #14063, where mirrored-mode policy routing of 127.0.0.1 breaks local :53 and Docker's nftables backend. https://github.com/microsoft/WSL/issues/14063
- Docker default address pools are '172.17.0.0/12 in /16s': IMPRECISE. They are 172.17.0.0 through 172.31.255.255 as /16s, then 192.168.0.0/16 as /20s. The WSL NAT subnet is chosen by HNS and its overlap with these pools is not guaranteed. https://raw.githubusercontent.com/moby/moby/master/daemon/libnetwork/ipamutils/utils.go
- Premise in the brief that Docker 28 does nftables: WRONG. Docker 28.x uses only iptables. An nftables firewall backend arrived experimentally in Docker 29.0 (tables ip/ip6 docker-bridges); it has no DOCKER-USER chain, and since 29.6 it shells out to nft. https://docs.docker.com/engine/network/firewall-nftables/
- OS resolvers never treat *.localhost specially: PARTLY WRONG. systemd-resolved resolves .localhost to loopback, and .NET 11 now does too (dotnet/runtime#118569 closed). The let-localhost-be-localhost draft has expired; RFC 6761 still reserves .localhost. Windows' own resolver and many runtimes still do not.
- A resident daemon keeps the WSL VM alive and blocks vmIdleTimeout: WRONG. The distro instance ends after its Windows-side clients exit (about 15s by default; instanceIdleTimeout exists since WSL 2.5.4), and Linux processes do not keep it alive. vmIdleTimeout only starts counting after all distros stop. Discussion #41081 was misreported; the actual fix there was instanceIdleTimeout=-1. https://github.com/microsoft/WSL/discussions/41081
- 'WSL 3' paravirtualized architecture announced at Build 2026: FALSE. WSL PM Craig Loewen said on 2026-06-23 that 'there is no such thing as WSL 3'. https://www.windowslatest.com/2026/06/28/microsoft-denies-wsl-3-exists-reveals-windows-11s-wsl-containers-ship-next-week/
- Running the engine in its own distro avoids the hybrid cgroups on WSL 2.4.13: WRONG. Which controllers are v1 or v2 is decided by the single shared kernel. Fix it with WSL 2.5.1+ or a global cgroup_no_v1=all.
- Rancher Desktop's docker_engine proxy discovers the VM with a signature handshake: WRONG. wsl-helper races plain hvsock dials to registry-enumerated GUIDs with a 1s timeout and no signature. The signature handshake is in the separate networking package (host-switch), whose '10s' deadline appears only in a comment. Both use linuxkit/virtsock. rancher-desktop-networking has been archived since 2024-09-12. https://raw.githubusercontent.com/rancher-sandbox/rancher-desktop/main/src/go/wsl-helper/pkg/dockerproxy/platform/hyperv.go
- wsl --manage requires WSL 2.5+: WRONG except for --resize. --set-sparse has existed since 2.0.x and --move since 2.3.11. The 'sparse VHD disabled, use --allow-unsafe' block is documented from 2.5.x (#13075), not in #12103.
- Podman translates Windows bind paths only in the engine: WRONG. It converts on both sides: the Windows client resolves relative paths and checks existence, and the in-WSL engine converts again. \\wsl$ UNC paths are rejected. Docker Desktop's /run/desktop/mnt/host mapping has only secondary sources. https://raw.githubusercontent.com/containers/podman/main/pkg/specgen/winpath_windows.go
- WSL kernels have no AppArmor: TRUE FOR 5.15 ONLY. The 6.6 and 6.18 WSL kernels build AppArmor, but SELinux is the default exclusive LSM, so AppArmor stays inactive unless enabled on the kernel command line. apparmor_restrict_unprivileged_userns is an Ubuntu-only kernel patch.
- PSI is available for container pressure metrics: NOT ON THIS HOST. CONFIG_PSI is unset in the WSL 5.15 config; it is enabled in the 6.6 and 6.18 kernels.
- Windows Hypervisor Platform availability on Home is unverified: NOW VERIFIED LOCALLY. It is present but disabled on this Windows 11 Home host; enabling it needs elevation and a reboot. The Hyper-V role cannot be installed on Home.
- Docker Desktop 4.42 fixes the WSL 2.5.7 startup failure: x64 ONLY. On ARM64 it still failed (docker/for-win#14814). The Resource Saver polling fix shipped in 4.89.0, and the for-win issues cited earlier are general vmmem complaints, not Resource Saver bugs.
- virtiofs bug #40773 is a current known bug: CLOSED. virtiofs shares are served by wsldevicehost, not the Plan9 server. Other virtiofs bugs remain open, e.g. #40719, where files show up root-owned. There is no evidence that virtiofs fixes inotify for edits made on the Windows side.
- Consomme gives the guest a DHCP address: UNCERTAIN. WSL's ConsommeNetworking may configure the address statically. Consomme also silently drops fragmented packets (UDP over about 1472 bytes) and IPv6 ping. The 'consomme' networkingMode value is not yet in the Learn docs (they still say virtioproxy).
- docker-proxy in 28.0 'cannot accept connections before NAT rules exist': REPHRASE. The change closed a window where the proxy could accept connections that later broke once NAT rules were installed. 28.0 also stopped adding masquerade rules for a container's own published ports when the userland proxy is enabled.
- Docker Desktop on Windows uses the gVisor network stack: UNCONFIRMED. gVisor is confirmed as the default only on Mac; the 2022 blog describes the design, not the current Windows implementation.
- Docker Hub anonymous limit of 100 per 6 hours: UNRESOLVED CONFLICT. The docs (modified 2026-09-03) say 100 per 6h, while a 2026-09-13 probe returned the header ratelimit-limit: 100;w=3600. The announced 10/hour limit was not enforced, and secondary sources that say it was are wrong.
- Performance figures (crun 2x runc, youki 111ms, Firecracker ≤125ms/≤5MiB): CAVEAT. These are old self-reported project benchmarks or bare-metal specs. They have not been validated on current versions or under nested virtualization on WSL2, so re-measure before relying on them.
- Go SysProcAttr.NoNewPrivs and UseLandlock: TENTATIVE. They exist on Go master but not in go1.27.1 (the latest release as of 2026-09-13).
- WSL 2.9.x distro cgroup isolation delegates all controllers: UNVERIFIED. PR #40519 only mentions memory and cpu in subtree_control; pids, io, cpuset and hugetlb need to be probed.

## WSL constraints

- The host is outdated: WSL 2.4.13 with kernel 5.15.167.4. Current stable is 2.7.14 (2026-09-11) on 6.18-line kernels, and pre-release is 2.9.11. WSL 2.5.1 moved to kernel 6.6 and removed cgroup v1 mounting. Upgrade WSL before designing kernel-dependent features, and treat 5.15 as a degraded mode. The Microsoft Learn kernel release-notes page is stale, so use the GitHub releases instead. https://github.com/microsoft/WSL/releases/tag/2.5.1
- cgroups are currently hybrid: v1 controllers are mounted and cgroup2 at /sys/fs/cgroup/unified has no controllers. Controller binding belongs to the single shared kernel, so creating a separate distro does not give you v2. The fixes are `wsl --update` (2.5.1+) or `kernelCommandLine = cgroup_no_v1=all` in .wslconfig, which applies to every distro including docker-desktop. On 2.5.1+ you can opt back into v1 with `[automount] cgroups=v1`. https://docs.kernel.org/admin-guide/cgroup-v2.html
- WSL 2.9.x pre-releases add isolateDistroCgroup (default true): each distro lives under /wsl-user/distro-<pid> in its own cgroup namespace. Memory is capped at VM RAM minus 32MiB, and cpu.max holds back 0.01 core. Only memory and cpu are confirmed in subtree_control; pids, io, cpuset and hugetlb are unverified, so probe cgroup.controllers. https://github.com/microsoft/WSL/pull/40519
- All WSL2 distros share one VM, one kernel, one network namespace and one netfilter ruleset. Running alongside Docker Desktop means shared port space, Docker's iptables FORWARD DROP (an accept in your nftables chain does not override it), and competition for the \\.\pipe\docker_engine pipe. The only isolation between distros is mount, PID and UTS namespaces. https://raw.githubusercontent.com/microsoft/WSL/master/doc/docs/technical-documentation/init.md
- Every .wslconfig [wsl2] setting (memory, which defaults to 50% of RAM and is about 8GB here; kernelCommandLine; networkingMode; vmIdleTimeout; nestedVirtualization) applies globally. Changes need `wsl --shutdown`. vmIdleTimeout and nestedVirtualization are Windows 11 only. https://learn.microsoft.com/en-us/windows/wsl/wsl-config
- Lifecycle: a distro instance is terminated after its Windows-side clients (wsl.exe or other CreateInstance callers) exit. The default timeout is about 15s, and `[general] instanceIdleTimeout` (WSL 2.5.4+, not on this host) changes it. Linux background daemons do NOT keep the instance alive. vmIdleTimeout (60000ms) only starts counting once every distro has stopped. The engine therefore needs a deliberate keep-alive, such as a long-lived wsl.exe agent. https://raw.githubusercontent.com/microsoft/WSL/master/src/windows/service/exe/LxssUserSession.cpp
- Init: WSL's /init runs as PID 1 in each distro unless `[boot] systemd=true`. `[boot] command` (Windows 11) runs as root when the instance starts and can launch the supervisor. With systemd, set up a delegated cgroup subtree (Delegate=yes) and follow the single-writer rule. https://wsl.dev/technical-documentation/systemd/
- Windows-to-VM transport: Windows AF_UNIX interop into WSL2 does not work (issue #5961, open). hvsock (AF_HYPERV / AF_VSOCK, service GUID <port>-facb-11e6-bd58-64006a7986d3) needs the WSL VM's runtime ID, which is regenerated on every VM start. Wildcard VmId listeners do not accept connections from the WSL VM. The known ways to find the ID are hcsdiag or HCS enumeration (needs admin), the HostComputeService VolatileStore registry key (has broken after WSL updates), or a HKCU Terminal Server Client value; none is a supported API. WSL grants hvsocket bind and connect to SYSTEM plus the launching user. https://github.com/nbdd0121/wsld/blob/master/docs/impl.md
- Fallback transports: `wsl.exe --exec` stdio works (output is UTF-16LE unless WSL_UTF8=1, and each call starts a new process). TCP on localhost works in NAT mode but has no authentication and is exposed to DNS rebinding from browsers.
- NAT-mode localhost forwarding relays only TCP LISTEN sockets. It discovers them by polling sock_diag every second and connects to 127.0.0.1 or ::1 inside the VM. UDP is never relayed. A listener bound to a specific non-loopback VM IP gets a Windows listener but the relay fails. A port published only through nftables DNAT, with no socket in the root network namespace, is invisible. NAT mode has no IPv6. Since WSL 2.3.25, NAT can silently fall back to VirtioProxy. https://raw.githubusercontent.com/microsoft/WSL/master/src/linux/init/localhost.cpp
- Mirrored mode (Windows 11 22H2+): a seccomp user-notify hook intercepts bind and listen only in the tracker's own network namespace, so listeners inside container netns are untracked. Windows localhost traffic arrives on loopback0 and must be exempted from DNAT (moby#48075, which needs a userland proxy). ::1 is unsupported between Windows and Linux. The Hyper-V firewall blocks inbound traffic by default. Open issue #14063: policy routing of 127.0.0.1 breaks local :53 and Docker's nftables backend. https://github.com/microsoft/WSL/issues/14063
- Consomme mode (VirtioProxy renamed in 2.9.3 pre-release, and the default for wslc) is user-mode NAT from OpenVMM using the seccomp port tracker. Docker DNAT of Windows->127.0.0.1 traffic breaks (#41554, open). It drops multicast and broadcast, IP fragments (large UDP), IPv6 ping, GRE, ESP and SCTP, and does not forward ICMP errors. https://openvmm.dev/guide/reference/backends/consomme.html
- The NAT subnet is chosen by HNS and usually falls inside 172.16.0.0/12, which can overlap Docker-style pools (172.17-172.31 as /16s) and VPN ranges. With DNS tunneling, resolv.conf points at 10.255.255.254, so upstream DNS must be queried from the host network namespace.
- File sharing: /mnt/c is DrvFs over Plan 9 via a Hyper-V socket, measured at about 7x slower writes and about 60x slower metadata operations. Edits made on the Windows side raise no inotify events. virtiofs (`virtiofs=true`) is opt-in, served by wsldevicehost, has open bugs such as root-owned files (#40719), and its 2026 speedups need 6.18 pre-release kernels. Keep images, containers and volumes on the distro's ext4 VHDX. https://learn.microsoft.com/en-us/windows/wsl/filesystems
- LSMs: the 5.15 WSL kernel has no AppArmor. The 6.6 and 6.18 kernels build AppArmor in, but SELinux is the default exclusive LSM, so AppArmor stays inactive unless enabled on the kernel command line. apparmor_restrict_unprivileged_userns does not exist on Microsoft kernels. Build hardening on user namespaces, seccomp, capabilities, NNP, masked paths and Landlock (ABI 1 on 5.15).
- What kernel 5.15 has: clone3, CLONE_INTO_CGROUP, pidfd plus setns(pidfd), cgroup.kill, the new mount API, mount_setattr idmap for ext4 and btrfs, rootless overlay (5.11+), unprivileged whiteout mknod (5.8+), openat2. What it lacks: idmapped overlay layers (5.19), idmapped tmpfs (6.3), lowerdir+ (6.7+), MOVE_MOUNT_BENEATH (6.5), PSI (CONFIG_PSI unset), newer Landlock ABIs, and the sysctl for disabling TIOCSTI (6.2). The memory.kmem v1 limit is still enforced on 5.15. OPEN_TREE_NAMESPACE (7.0) is missing even from WSL's 6.18 kernel.
- Overlay config on 5.15 has redirect_dir, metacopy, index and xino all off, verified by probe, so diffing the upperdir directly is valid. The newer WSL 6.6.y config sets OVERLAY_FS_REDIRECT_ALWAYS_FOLLOW=y, so always pass redirect_dir=off,metacopy=off,index=off explicitly. The legacy mount-option string is limited to one page, so use short link names.
- The WSL 6.18 kernel falls in the range runc 1.5.0 lists (6.17 to 7.2) for memory corruption when configuring cgroup v2 device rules. Copy runc's workaround or keep device BPF programs minimal. https://github.com/opencontainers/runc/blob/main/CHANGELOG.md
- Virtualization: nested KVM works in normal distros (/dev/kvm is present, vmx exposed) but not in wslc sessions (#40736). Windows 11 Home has no Hyper-V role. Windows Hypervisor Platform is present but disabled on this host; enabling it needs elevation and a reboot.
- Competition and churn: Microsoft's WSL Containers (wslc.exe, pre-release 2.9.3+, GA targeted for fall 2026) brings virtiofs, Consomme, GPU support and SDKs, but no Docker API and no Compose yet. Microsoft's PM has said 'WSL 3' does not exist. https://devblogs.microsoft.com/commandline/wsl-container-is-now-available-for-public-preview/
- Disk: sparse VHD is disabled because of possible corruption (it requires --allow-unsafe on 2.5.x+). `wsl --manage --resize` needs 2.5+; --move (2.3.11) and --set-sparse (2.0.x) are older. The .wsl distro format needs 2.4.4+.
- Docker Desktop in WSL usually configures credsStore 'desktop.exe', a Windows credential helper. A Linux-side engine must be able to call it or keep its own credential store.
- Toolchains: the Windows host has no Go or Rust. The Ubuntu distro is stopped; build the Linux engine there or cross-compile. cgo-based nsexec is easiest to build natively inside WSL.

## Top risks

- Scope explosion from the Docker Engine API long tail: hijacked attach/exec with stream framing, events, archive, filters, error semantics, and BuildKit /grpc + /session. This is XL solo work. Mitigate by reusing moby API types, crun and buildkitd, and by building a conformance harness early. https://raw.githubusercontent.com/moby/moby/master/api/swagger.yaml
- Container escapes from a hand-written root runtime. Every recent runc CVE class came from path-based operations on attacker-controlled rootfs or procfs: CVE-2019-5736 (/proc/self/exe overwrite), CVE-2024-21626 (leaked fd used as cwd), and CVE-2025-31133/52565/52881 (/dev/null and /dev/console symlink swaps, redirected LSM writes). The three references are all vulnerable. Mitigate with the fd-based mount API, openat2 RESOLVE_IN_ROOT, user namespaces by default, a CVE regression suite, and crun as the default until the custom runtime passes that suite. https://www.cncf.io/blog/2025/11/28/runc-container-breakout-vulnerabilities-a-technical-overview/
- The host platform is outdated and changing fast. WSL 2.4.13 runs kernel 5.15 with hybrid cgroups. Upgrading changes the kernel (6.6 or 6.18), removes cgroup v1, and brings new networking modes (Consomme) and distro cgroup isolation, all of which also affect Docker Desktop in the same VM. Several features only exist in pre-releases.
- Windows localhost reachability depends on the WSL networking mode. NAT relays only TCP listeners, polled every second, and never UDP. Mirrored mode needs loopback0 excluded from DNAT. Consomme breaks DNAT from 127.0.0.1. A DNAT-only port-publishing design will look broken from Windows browsers and from Testcontainers. https://github.com/microsoft/WSL/issues/41554
- Coexistence with Docker Desktop inside one shared VM: Docker's iptables FORWARD DROP blackholes packets from your bridges, the \\.\pipe\docker_engine name is contested, .wslconfig and kernelCommandLine settings are global, and host ports collide.
- Distro lifecycle and transport fragility. WSL terminates the engine distro when no Windows client is attached, regardless of Linux daemons. hvsock needs the runtime VM ID, and the registry location Rancher relies on has disappeared after a WSL update before. Without a keep-alive and a fallback transport, the engine goes away unexpectedly. https://github.com/rancher-sandbox/rancher-desktop/issues/3139
- Dependence on the build path. The docker CLI and Compose v5 route builds through buildx/Bake, which requires the /grpc and /session endpoints that API v1.53 deprecated. A native builder is L to XL effort, and failed builds are the first thing a daily-driver user notices.
- Language and runtime mismatch in Go. The runtime cannot setns into user or mount namespaces after it starts, so exec requires a cgo C constructor or a separate non-Go binary. That complicates cross-compilation, and the /proc/self/exe re-exec pattern reintroduces the CVE-2019-5736 risk.
- Microsoft's wslc may make the project redundant. It is free and first-party, reaches GA in fall 2026, and already has virtiofs, Consomme networking, GPU support and SDKs. If Microsoft adds Compose or a Docker API, basic parity loses its value. Differentiate on Docker API compatibility and developer experience. https://devblogs.microsoft.com/commandline/wsl-container-is-now-available-for-public-preview/
- Image and storage correctness bugs: whiteout and opaque-directory ordering, hardlinks, and path traversal in the layer applier. Also the overlay mount-option page limit (about 60 layers with long paths), inconsistent manifest types from registries (Docker Hub returns whatever was pushed, including schema1 on old tags), and no idmapped overlay on kernel 5.15.
- File-sharing performance and hot reload. Projects on /mnt/c are slow over 9P, and edits made in Windows produce no inotify events inside WSL. virtiofs is opt-in, depends on pre-release builds, and has bugs. Users will blame the engine.
- Kernel bugs in the target kernel: runc 1.5.0 documents memory corruption when configuring cgroup v2 device rules on kernels 6.17 through 7.2, and WSL ships 6.18. PSI is not available on 5.15.
- Resource ceiling: the VM has about 8GB RAM shared with Docker Desktop and other distros. cgroup.freeze stops CPU use but keeps memory resident. Memory only goes back to Windows through guest reclaim or a full VM shutdown.
- Docker Hub rate-limit uncertainty. Docs say 100 anonymous pulls per 6h, but a probe saw a 100;w=3600 header. Aggressive re-pulls during development could get throttled.

## Docker Engine API compatibility

Recommendation: yes. Make a tiered Docker Engine API subset the main compatibility surface rather than cloning docker CLI flags. The stock docker CLI, docker compose v5, VS Code Dev Containers (which drives the docker CLI through dev.containers.dockerPath and needs exec, inspect, ps with label filters, events in JSON format, and build with --build-context) and Testcontainers all work unchanged against a Docker-compatible endpoint. Microsoft's wslc preview has no Docker API, so this is the clearest unfilled gap on Windows.

1. Endpoints
- Serve the same handler on unix:///run/<engine>/docker.sock, on /mnt/wsl/<engine>/docker.sock (the tmpfs shared across distros), and, via the Windows bridge, on \\.\pipe\<engine>.
- Also claim \\.\pipe\docker_engine, but only if it is free, since Docker Desktop, Podman and Rancher Desktop all compete for it. Detect conflicts, fall back to a named docker context, and restrict pipes with a user-only SDDL.
- The bridge must relay raw bytes with half-close support (CloseWrite). An HTTP-aware proxy would break hijacked attach/exec, h2c and stdin EOF.
- Sources: https://github.com/containers/podman/blob/main/docs/tutorials/podman-for-windows.md, https://github.com/rancher-sandbox/rancher-desktop/issues/7169

2. Versioning
- Answer GET and HEAD /_ping with API-Version, OSType: linux, Builder-Version and Docker-Experimental headers, plus /version with ApiVersion and MinAPIVersion.
- Accept every route with and without the /v{version} prefix, as Podman does.
- Advertise a maximum of at least 1.44, because Docker 29.0-era clients and SDKs set 1.44 as their minimum. Advertise 1.40 as the minimum; Docker 29.3 lowered its own minimum back to 1.40, and Engine 29.8 supports 1.40–1.56.
- Raise the maximum only as newer request fields are actually handled.
- Sources: https://docs.docker.com/reference/api/engine/, https://docs.docker.com/engine/release-notes/29/

3. Tiers
- Tier 0: /_ping, /version, /info, GET /containers/json, GET /images/json.
- Tier 1, the docker run/exec/logs flow:
  - POST /containers/create must return a Docker-shaped 404 "No such image" so the CLI pulls and retries.
  - POST /images/create streams JSON progress and uses X-Registry-Auth.
  - POST /containers/{id}/attach answers 101 UPGRADED with Upgrade: tcp, using application/vnd.docker.raw-stream for TTY and multiplexed-stream otherwise, with 8-byte [type,0,0,0,len] frames.
  - POST /containers/{id}/wait with condition=next-exit|removed.
  - /start, /resize, /stop, /kill, GET /containers/{id}/json, /logs, DELETE.
  - POST /containers/{id}/exec, /exec/{id}/start (hijacked), /exec/{id}/resize and /json.
  - GET /events.
- Tier 2, for Compose and Testcontainers: /networks CRUD plus connect/disconnect; /volumes; label filters on list endpoints; HEAD/GET/PUT /containers/{id}/archive with X-Docker-Container-Path-Stat; image inspect, tag, delete and prune; /containers/prune; stats.
- Tier 3: build.
- Source: https://raw.githubusercontent.com/moby/moby/master/api/swagger.yaml

4. Build (highest risk)
- For Linux daemons the modern CLI routes `docker build` through buildx. buildx's docker driver needs POST /grpc (h2c upgrade) and /session.
- Podman lacks these, and docker build fails with "unable to upgrade to h2c, received 404".
- API v1.53 marked /grpc and /session deprecated without a stated replacement.
- Compose v5 hands all builds to buildx bake.
- Recommended approach:
  - Bundle buildkitd in the engine distro and preconfigure a buildx remote-driver builder pointing at it.
  - Import build results into the engine store.
  - Optionally proxy /grpc and /session to buildkitd for default-driver compatibility.
  - Keep legacy POST /build for DOCKER_BUILDKIT=0.
  - Re-check current buildx and compose behavior before committing.
- Sources: https://github.com/containers/podman/issues/17836, https://docs.docker.com/reference/api/engine/version-history/, https://github.com/docker/compose/releases/tag/v5.0.0-rc.1

5. Server-side semantics clients depend on
- Translate Windows bind sources in the engine:
  - C:\x, c:/x and /c/x become /mnt/c/x.
  - Reject \\wsl$ and \\wsl.localhost UNC paths with a clear error.
  - Map //./pipe/docker_engine and /var/run/docker.sock to the engine socket so the Ryuk container and Docker-in-Docker work.
- Apply Entrypoint and Cmd exactly as Docker does.
- Preserve com.docker.compose.* and devcontainer.* labels verbatim.
- Report State.Health and health_status events.
- Publish ports with real listeners in the VM root network namespace, because Testcontainers connects to mapped ports on Windows localhost (TESTCONTAINERS_HOST_OVERRIDE and TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE are escape hatches).
- Keep a sane `docker -v` and version string, because the devcontainers CLI checks for 'podman' or 'wslc' and changes its behavior.
- Sources: https://golang.testcontainers.org/features/configuration/, https://github.com/devcontainers/cli/blob/main/src/spec-shutdown/dockerUtils.ts

6. Process
- Treat compatibility as XL effort.
- Drive it with a conformance harness that runs the real docker CLI, compose sample projects, testcontainers-go and a Dev Container open, logging which endpoints and fields each run uses.
- Reuse the moby/moby api and client Go types for exact JSON shapes.
- Do not implement Swarm, plugins or Windows containers.
